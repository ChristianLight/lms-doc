# Joomla 6 implementation roadmap

This companion proposes one implementation of the platform-neutral LMS specification. It sets the extension boundaries, assigns data ownership, and describes how to build and verify a Joomla Component Builder (JCB) project. The component names and view budgets are proposals for the implementation backlog.

## Feasibility and first release boundary

Joomla can provide the site, authentication, sessions, group-based permissions, extension packaging, form infrastructure, routing, language files and scheduled task entry points. JCB can generate and maintain routine administrator views, selectors, fields, data retrieval and site layouts. The LMS still needs explicit services for publishing immutable revisions, resolving learner access, accepting timed submissions, grading, releasing grades and converting imports. A JCB blueprint is maintained build source. A curriculum package is LMS data processed through the runtime import workflow. [Joomla User API](https://manual.joomla.org/docs/general-concepts/user/) · [JCB request-to-extension workflow](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/workflows/request-to-extension.md)

The highest uncertainty is whether a curriculum export preserves enough information to reproduce the behavior of the original course. HTML and XML can carry structure and configuration. A live course may also rely on runtime-specific scripts, grader algorithms, external tools, asset permissions and versioned library content. A new GUID supplies identity for an imported object. Behavior equivalence comes from mapping each supported construct and checking the resulting learner experience and marking outcomes. A curriculum migration spike should precede a full editor and assessment build. Use synthetic fixtures initially. Add representative, de-identified course and library exports when available.

SCORM playback is another implementation stream. Its runtime and browser security requirements are independent of both the curriculum importer and native exam services. Release each documented SCORM profile against package fixtures and supported browser versions. Keep the launch bridge and untrusted package assets outside the authenticated Joomla page context. Serve the player shell and the shareable content object under an isolated origin where the content can discover the synchronous browser API object. Keep the Joomla authentication cookie host-only. Use a short-lived, attempt-bound launch grant for the runtime endpoint and validate every mutation against its package revision, session and permitted fields. Reconcile interrupted commits and surface unsaved state. Treat package-reported scores as third-party evidence with explicit gradebook policy. [ADL SCORM 1.2 cross-domain guidance](https://www.adlnet.gov/assets/uploads/ADL_CrossDomainScripting_1_0.pdf) · [ADL SCORM 2004 4th Edition testing requirements](https://adlnet.gov/assets/uploads/SCORM_2004_4ED_v1_1_TR_20090814.pdf)

## Extension layout

Use one required Joomla package that installs cooperating components, a shared contracts library and the required runtime plugins. Make separately installed collaboration and document adapters optional. Keep one operational database for the first implementation and use clear table ownership, public service contracts and domain events to preserve component boundaries. [Joomla package manifests](https://manual.joomla.org/docs/building-extensions/install-update/installation/package/)

The budget below is for top-level administrator workspaces. An editor can present multiple tabs, modal selectors and contextual actions within a workspace. Build a workspace only when a staff role has an operation to perform there.

| Proposed component | Owns | Administrator workspaces | Site entry points |
| --- | --- | --- | --- |
| `com_lmsadministration` | Institution and academic calendar records, account-to-person mapping and institution-level role assignments | Institutions and units, Academic periods, People and account links, Institutional roles, Administration audit | Access and onboarding status where needed |
| `com_lmscurriculum` | Course and CourseVersion, reusable content and libraries, ContentNode and ContentNodeVersion, ContentPlacement, Activity and ActivityVersion | Courses, Outline and activity editor, Content libraries, Assets and links, Publication review | Course catalogue, permitted preview |
| `com_lmsdelivery` | CourseOffering, Section, LearningGroup, Enrollment, teaching assignments, pacing and completion evidence | Offerings, Sections and rosters, Learning groups, Enrollments, Progress and exceptions | My learning, Course player, Course staff workspace |
| `com_lmsassessment` | Item bank, assessment definitions and versions, AssessmentDelivery, attempt and response records, grading evidence and moderation | Question bank, Assessments, Exam deliveries, Marking and moderation, Attempt operations | Assessment player, Submission review, Assessor workspace |
| `com_lmsrecords` | Gradebook policy, GradeResultRevision, publication batches, official reports and transcript records | Grade policies, Gradebook, Publication and corrections, Reports and transcripts | My grades, Released report cards and transcripts |
| `com_lmsinteroperability` | Import and export jobs, source archives and identity maps, compatibility diagnostics, SCORM package revisions and sessions | Import jobs, Import diagnostics and mappings, SCORM packages, Runtime diagnostics, Export jobs | SCORM launch entry, with player and API bridge on an isolated origin |

Curriculum owns the Activity and its placement. An assessment ActivityVersion refers to the exact assessment definition revision by a contract identifier. Delivery owns the learner's offering and eligibility context. Assessment owns the frozen delivery rules, response evidence and scoring decisions for a learner attempt. Academic Records owns the grade version that is visible or official. A score import or manual correction follows the same authorized Academic Records commands and audit rules.

Separate staff workspaces from the general Joomla administrator role. Offer course delivery, routine marking and grade review through scoped site views where practical. Reserve platform configuration, broad exports and operational recovery for administrators with explicit capability grants.

### JCB view budget and schema ownership

The JCB normalized-subform workflow requires an attached Admin View for each separately persisted child table managed by that workflow. Hiding a child editor from the menu reduces navigation and leaves the underlying Admin View in the blueprint. The normalized storage and save lifecycle depend on that attached child view. [JCB normalized subforms](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/packages/workflows/normalized-subforms.md)

Set a first-slice target of at most five visible workspaces and five JCB Admin View definitions per component where practical. Use the generated record views for the few objects staff genuinely administer. A workspace for publishing, moderation or replay can be a custom task screen. Store immutable revisions, relationships, responses and event records through versioned SQL and the owning service where generated CRUD would bypass their lifecycle. If an authorized editor needs an additional JCB-normalized child Admin View, keep its permissions and schema explicit, and decide whether to allow an internal Admin View or split the responsible component. Prototype one course outline editor and one assessment definition editor to check the exact generated view count, asset rules and installer schema before fixing the component boundary.

The shared library should define only cross-component interfaces and common types such as actor and scope, revision identifiers, domain event envelopes and error contracts. Owners implement their own authorization decisions and persistence. Site forms, administrator forms, web APIs and scheduled jobs call the same commands. Other components may read a published interface or scoped projection. Writes go through the owner, including imports and administrative repair. Use Joomla form definitions and core input validation for configuration, roster and staff forms. Build domain-backed site forms for typed item responses, formulas and timed exams. Reuse the same server-side validation and idempotent submission commands across the form, accessible alternatives and API. A packaged task or console plugin runs worker batches with named locks, bounded work, health metrics and retry schedules. Use system cron or an equivalent reliable runner for grading and migration workloads. [Joomla scheduled tasks](https://guide.joomla.org/user-guide/scheduled-tasks)

## Identity and access

Use Joomla accounts for sign-in, MFA configuration, session lifecycle, account block state and coarse access. Link the Joomla local numeric user ID to a stable LMS person GUID. Make the link unique within the installation and preserve external subject IDs with their issuer. Reconciliation is an explicit operation with audit evidence. Educational records can continue to reference the person after the account is blocked or removed, subject to institution retention and erasure rules. Leave passwords and authentication credentials with the identity provider.

Use Joomla groups and viewing access levels for coarse administrative capabilities, menus and optional catalogue visibility. Use application role assignments for the institution, course offering, section, learning group and activity where the LMS needs narrower authority. In particular, a teacher can teach one section and study in another with one Joomla account. Use coarse Joomla permission plus the relevant LMS relationship, state and release checks on every protected command and query. Examples include `curriculum.publish`, `offering.manage`, `assessment.mark`, `records.release` and `interop.import`. Define local Joomla action mappings in component ACL declarations, with the capability and scope mapping reviewed centrally. Restrict emergency administration separately and audit its use. [Joomla action permissions](https://manual.joomla.org/docs/general-concepts/acl/acl-permissions/) · [Joomla access levels](https://manual.joomla.org/docs/general-concepts/acl/acl-access/)

| Request | Authority required |
| --- | --- |
| Learner resumes a lesson | Active access to the offering and the exact placement, after availability and prerequisite checks |
| Teaching assistant marks work | Marking capability and assignment for the applicable delivery and learner scope, with approved marking fields |
| Moderator releases a grade batch | Explicit release permission for the scope, moderation conditions met, and an auditable release command |
| Staff downloads a private attachment | File access derived from the exact content or submission relation and current visibility of that revision |
| AI service proposes course changes | Explicit draft-authoring capability for the target course or library, request attribution and human publication approval |

Carry the actor and scope through background work. The web handler must validate the actor and requested resource before queueing work. The worker must enforce the saved job authority and resource state when executing it. Use anti-CSRF protection for Joomla session writes, separate API credentials with narrow capabilities, and reject object access through guessed identifiers. Keep answer keys, hidden rubric notes and unreleased grades out of generated API payloads, exports for learners, shared caches and client-side code. Confirm generated menus, endpoints and list queries obey the same permission policy.

## Data and upgrade contract

- Retain Joomla numeric row IDs where required by the MVC, asset and table conventions. Use immutable application GUIDs as public identifiers and portable relations between LMS entities. Keep blueprint definition GUIDs, application GUIDs, human course codes and source package identifiers in separate namespaces. Use canonical GUID encoding consistently across tables and require unique constraints. Mappings should keep the original source key and identify its scope and version. [JCB application identities](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/packages/workflows/application-identities.md)
- Build install SQL and versioned upgrade SQL for the selected database dialect. Define owners and migration order in a compatibility manifest. The fresh install must contain the full current schema. Test skipped-version upgrades, an interrupted migration and restart. Use staged migrations and explicit backups where DDL cannot be rolled back. Treat schema changes, application package versions and curriculum interchange schema versions as separately tracked values. Start with a tested database matrix and expand advertised support only after verifying engine-specific migrations and concurrency behavior. [Joomla extension manifests and SQL updates](https://manual.joomla.org/docs/building-extensions/install-update/installation/manifest/#sql-schema-numbering)
- Enforce same-owner references, legal states and uniqueness in the database where supported. Use service-level ownership and existence checks, indexed references and deletion restrictions across independently upgradeable components. Preserve published content and academic records through archival, retention and export workflows. Package installation must fail preflight for a missing required dependency or incompatible schema. Test component uninstall behavior and require an explicit institution data-purge procedure.
- Write a command's business result and its outgoing event to one transaction where the owner stores them together. Assign each retried command an idempotency key. For example, submission creates one terminal attempt record and one grading request even when a browser repeats a timed-out call. Reconciliation detects a missing projection or an event that was handled twice. Grade screens report a pending state while asynchronous projections catch up.
- Keep high-volume attempt, response and audit tables separate from catalogue and authoring queries. Index common owner-scoped lookups, including person and offering, delivery and attempt, and grade result and revision. Keep transactions short. Store large package binaries and media through a private storage provider with digest and revision metadata. Measure exam-window traffic and worker lag before tuning database partitioning or deployment topology.

## Collaboration, files and media

| Capability | First implementation | Interface and authority |
| --- | --- | --- |
| Class chat and video meetings | Open the provisioned private Nextcloud Talk conversation from the course or section | The LMS owns class access. Nextcloud owns chat and call content. Maintain scoped remote conversation and participant bindings. |
| Collaborative file sharing | Use designated Nextcloud group shares where needed for course discussions and collaboration | Keep sharing within approved group boundaries. Refresh remote grants and revoke departed users. |
| Course documents and controlled attachments | Reuse Filery through a document adapter after verifying the installed product's contract | Reference provider, opaque file ID, immutable version or verified digest, media type and permitted purpose. The LMS owns the document's relationship to a lesson, assessment or submission. |
| Lesson video | Render an approved managed or external media reference with captions and transcript | The LMS owns activity availability and learning policy. A player event can provide viewing evidence under an explicit completion rule. |
| Course generation | Give an AI service access to the typed authoring commands and preview endpoint | Require provenance, validation, revision checks, review and separate publication permission. |

For Nextcloud, negotiate server and Talk capabilities. Define one provisioning strategy per deployment for accounts and groups, with stable remote IDs and an explicit administrator choice of identity federation or account mapping. Avoid matching accounts by display name or email alone. Provision private rooms with intended moderators, reconcile membership from active LMS assignments and account status, and surface failures in operations. A timeout after room creation requires a lookup or reconciliation before retrying creation. Check removal paths for direct and group-derived access. Refresh periodic reconciliation to catch drift when a participant or group changes remotely. Collaboration outages should allow native lessons, exams and grades to continue. [Nextcloud provisioning API](https://docs.nextcloud.com/server/stable/admin_manual/configuration_user/user_provisioning_api.html) · [Talk conversations](https://nextcloud-talk.readthedocs.io/en/stable/conversation/) · [Talk participants](https://nextcloud-talk.readthedocs.io/en/stable/participant/) · [Nextcloud Share API](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-share-api.html)

Verify the exact Filery product, revision, endpoint or extension interface and authentication scheme in the deployment before estimating implementation effort. Test whether it supports private reads, revision retrieval, uploads with size and type restrictions, scan status and expiring access. If it serves mutable files only, store the approved immutable revision in the LMS media store or make that resource explicitly unsuitable for immutable graded content. Authorize each retrieval against LMS context before issuing a short-lived link or streaming a file. Keep student submissions private by default and distinguish the right to view a course from the right to see another learner's evidence. Preserve quarantined archive storage for import regardless of the document provider.

## JCB delivery workflow for an agent

1. Choose a vertical slice and write its actor, data ownership, permission checks, state transitions, failure modes and observable acceptance cases. Use the approved Joomla 6 minor release and server runtime. Resolve the production JCB release at implementation time and record the exact tested releases and source revisions. Confirm the actual authoring environment supports the required operations. [Joomla 6 technical requirements](https://manual.joomla.org/docs/get-started/technical-requirements/) · [JCB version policy](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/standards/version-policy.md)
2. Start from the current JoomEngine entry point. Use an authorized JCB site, a suitable Playground build environment, or supported repository blueprints with fresh import and compilation. Inspect the relevant model and use the official catalogues for suitable Fields, linked Admin Views, Dynamic Gets, Site Views, templates and layouts. Distinguish unchanged reuse from independently adapted definitions and retain references to their dependencies. Use Dynamic Gets for straightforward retrieval only when they satisfy the scoped policy. [JoomEngine JCB entry point](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/SKILL.md)
3. Add runtime behavior through project-owned services or reusable Super Powers, with stable interfaces and explicit callers in the correct JCB hooks. Use Joomla Powers when referring to supported core classes through the compiler. Keep authored PHP, assets, service registrations and versioned SQL in the maintainable source. Inspect actual compiler output, namespace placement and loaders in all required Joomla clients. [JCB PHP customization](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/super-powers/workflows/customize-extension.md)
4. Compile components and assemble a package. Verify a clean runtime installation independently of the authoring site, then test upgrades, denial paths and real user behavior on a server environment. Use Playground as a fast fixture for authoring and installation checks where supported. Use a production-like environment for reverse-proxy limits, cron workers, provider connections, separate-origin SCORM delivery, load tests and backup restoration. [JCB delivery and restoration](https://github.com/joomengine/skills/blob/e7b8723397811772c85358e72ce91ab594785748/workflows/delivery.md)
5. Retain editable blueprints, custom services and their exact dependency revisions, schema updates, fixtures, release ZIPs and checksums, build instructions, and a verification record. Reconstruct the build on a clean JCB instance. An installer package and a portable curriculum archive are separate release artifacts with distinct acceptance tests.

## Implementation increments

| Increment | Working outcome | Exit evidence |
| --- | --- | --- |
| 0. Curriculum and tooling spike | Inspect course and library archives, stage an import, render one representative unit and mark representative answer types. Generate and install the smallest cross-component Joomla package. | Inventory of item types, source identifiers, dependencies and unsupported behavior. Golden input and expected output fixtures. A clean compile and install with course and assessment editor schema checks. |
| 1. End-to-end pilot | A teacher drafts and publishes a course revision. A learner enrolls, resumes a lesson, submits an automatically marked exercise and reads a released result. | Automated validation of published immutability, scoped permissions, retry-safe submit and correct grade visibility. |
| 2. Class delivery and academic records | Scheduled and self-paced offerings, roster and class administration, assignment marking, exams, moderation, regrading and reporting. | Class isolation, timed exam and accommodation scenarios, grade audit and correction tests, reproducible report calculations. |
| 3. Curriculum and standards coverage | Expand conversion from the measured inventory, enable tested SCORM profiles, and add portable exports and validated AI draft authoring. | Conversion and launch tests with reference packages, documented coverage and limitations, answer-equivalence review by teachers, import idempotency and archived failure diagnostics. |
| 4. Provider and operational readiness | Private collaboration and document adapters, reconciliations, monitoring, restore and rollout. | Nextcloud membership revocation and timeout tests, Filery access and file revision tests, exam peak-load test, deployment and recovery rehearsal. |

Order delivery by the pilot school's curriculum and operational dependencies. Where a course requires SCORM or document attachments on day one, promote that contract and its acceptance tests into the pilot. Set exam capacity and recovery targets with the institution before promising a production launch.
