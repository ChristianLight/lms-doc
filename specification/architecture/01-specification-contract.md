# Specification contract and reading order

## Status and precedence

This repository specifies a learning management product and the evidence required to implement and release it. The architecture summaries under `docs/` describe the system at a high level. The chapters under `specification/` define domain behavior and its edge cases. The domain catalogs express the structured data and interface contracts. The generated `reference/` directory provides JSON Schemas, an OpenAPI description, an entity dictionary and acceptance cases from those catalogs.

A feature is complete in the specification when its actor, authorization, input, state transition, output, failure recovery and acceptance evidence are specified. An implementation is complete only after it satisfies that contract in the installed target environment. A valid catalog or schema provides a structural check. Behavioral tests must separately demonstrate the temporal, transactional and academic rules that schemas cannot express.

When two provisions disagree, use this resolution order and record the correction in the owning catalog and chapter.

1. A declared standards profile takes precedence for its protocol surface. For example, the selected SCORM edition governs its runtime method return values and error codes.
2. The owning domain's invariant governs its authoritative state, including cross-domain callers.
3. The versioned institutional policy governs permitted choices within that invariant.
4. The request's captured effective policy and revision govern an in-flight assessment or historical record.
5. Presentation defaults govern only fields or behavior that the higher levels leave unspecified.

A summary, example or generated interface must be corrected if it contradicts a governing invariant. Do not silently preserve an inconsistent generated artifact. Run the catalog validator after changing names or field semantics and regenerate references from the authored source.

## Product rules and standards

The proposed entity names and internal data model are product design choices. They provide an implementation-independent model that can be mapped to external standards. A standard's terminology and identifiers are preserved inside its adapter. Mapping an external class to a Section, or an external resource link to an ActivityVersion, does not establish equivalence for every feature of the external system.

Each adapter declares a version profile, supported objects, supported operations, normalization rules, extensions, limits, fixtures and expected incompatibility behavior. An implementation may support one profile before another. The release manifest identifies the capabilities actually tested. Import, export, authoring, delivery and scoring are separate capabilities even when they use the same archive family.

## Field interpretation

A required field must be supplied in the contract representation, except values explicitly generated by the owner on creation. A nullable field may contain JSON null. Omission, null and an empty collection have different meanings in updates. Every update command defines which of these it accepts. A missing field ordinarily means preserve the stored value. An explicit null clears only a field declared clearable. An explicit empty array replaces a complete collection only in commands that declare full-replacement semantics.

A published snapshot includes resolved defaults. A future configuration change cannot retroactively alter a captured policy. A mutable administrator form may display an inherited value, but its save request must distinguish inheritance from an explicit override. Inheritance uses a typed mode and an optional value, with modes such as `inherit`, `replace` and `clear`. An empty string is never a substitute for a missing relationship or a policy instruction.

All external identifiers are strings with their original case and namespace preserved. Display codes can be normalized for search in a separate column. UUIDs identify records but convey no permissions. A request containing a valid UUID still passes institutional scope and object access checks. Content digests establish byte identity. They do not establish intellectual ownership or authorization to reuse a resource.

## Normative artifacts

Each domain supplies a catalog with six collections or metadata groups.

- Entities define fields, logical types, nullability, keys, indexes, invariants, retention and state transitions.
- Commands define an actor-visible operation and its request, response, permission, concurrency, transaction, errors and emitted events.
- Events define immutable messages with producer ownership, version, payload, ordering and deduplication semantics.
- Permissions define a named action, eligible scopes and role templates. Role templates are initial configuration and can be narrowed by the institution.
- Scenarios define concrete preconditions, actions, authoritative expected results and fixture values.
- Catalog version identifies the structure of the catalog itself. Entity and event versions remain separate concepts.

The JSON Schemas validate contract representations, not a particular SQL layout. An implementation can introduce local integer keys, denormalized read models, partition keys and storage indexes while preserving public identities, ownership and invariants. It must not merge states that carry different academic or authorization meanings.

## Change classification

| Change | Classification | Required handling |
| --- | --- | --- |
| Correct an explanation without changing a field or outcome | Editorial | Review links and regenerate references if the catalog changed |
| Add an optional response field that old clients can safely ignore | Additive contract | Bump the minor contract version and test older consumers |
| Add an enum value that clients branch on | Potentially breaking | Version the profile or require capability negotiation |
| Change a required request field, interpretation or unit | Breaking | New command or major contract version and explicit migration |
| Change question marking behavior | Academic behavior change | New rule version, fixtures and separate regrade decision |
| Change access or retention policy | Institutional policy change | Effective date, impact review and applicable consent or authority record |
| Alter a published course | New publication | New snapshot and explicit offering or learner rollout |
| Correct an issued report | Record amendment | New issued revision with original retained and linked |

## Build evidence

An implementation work item links to its commands, entities and scenarios. Completion evidence includes the source revision, supported host/runtime versions, migration or install path, tests executed, observed failures and resulting artifact digest. A code generator's success message provides generation evidence. Installation and learner workflows provide separate evidence. The same distinction applies to import parsing versus faithful rendering and correct grading.
