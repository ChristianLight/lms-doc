# 10. Specialized profiles, branching and exam admission

Each assessment capability is approved by type, renderer and scoring profile. The mandatory baseline supports fixed and randomized sections with free or linear navigation, compatible renderers and server-side deterministic marking. Conditional forms and specialist capabilities require explicit deployment enablement, supported source fixtures and review. A course can use both fixed and specialized deliveries.

## Formal admission, retake and accommodation workflows

A formal delivery can require an ExamAccessGrant in addition to learner enrollment. A registered verifier or supervisor records a one-use credential with delivery, enrollment, approval scope, start window, authority and optional reason. The authorization service issues the actual short-lived token. Candidate input never asserts that reauthentication succeeded. Staff cannot grant exam entry to a learner outside the offering. The start transaction validates the scoped token and consumes the grant only when the attempt and receipt commit. An idempotent retry of the start receipt does not consume a second grant. Expired, revoked or previously consumed grant is denied without revealing restricted support details.

For assisted manual admission, an examiner locates a student by authorized roster reference, verifies the institutional identity procedure, grants an attempt within the published window and records the method code without copying identity documents into assessment. For external verification, a signed callback maps to an approved Principal and the exact enrollment and delivery. Consent and source details are held separately. A token minted for one delivery cannot start another. The public course list never shows verifier failure reasons.

AttemptAllowance adds a bounded number of starts or a separately approved deadline window for the candidate. The command specifies delivery, Enrollment or TeamSnapshot, the prior attempt if applicable, reason, quota count, validity window and owner. Keep the ordinal monotonic. Compute remaining attempts from published base limit and valid approved unconsumed allowances. Consume the earliest expiring eligible allowance only after base capacity is exhausted. A cancelled or expired unused allowance does not count. A granted resubmission can target a revised form only if the approval explicitly permits it. Gradebook policy continues to choose how later attempts are counted. No allowance mutates the old score.

With base limit one, attempt ordinal 1 sealed, and staff allowance A with one additional start valid [09:00,12:00), a start at 11:59 consumes A and commits ordinal 2. A lost response then retry yields ordinal 2. Another start after that sitting terminates is blocked unless another allowance applies. A grant expiring at 12:00 cannot be consumed at exactly 12:00. A deadline window in an allowance affects only the start window unless an independent approved delivery override changes candidate write cutoff.

## Delayed and interactive behavior profiles

A fixed exam saves drafts, checks public syntax and withholds score evaluation until submission. A formative item can allow explicit candidate `CheckPracticeResponse` commands, a configured tries limit and feedback. A check references acknowledged response revisions and exact expected item check sequence. It returns approved feedback only and records an immutable PracticeCheck; it never seals the assessment or emits GradeEvidence. A profile can allow a pre-submit hint, reveal after N wrong tries, or require moving to the next practice task after exhaustion. For a check that can influence a score, disclose penalties before starting and persist every accepted check as evaluation input. The baseline excludes hint penalties from academic evidence. Exam bank item keys and explanations must not be exposed through another practice placement without compatible release classification.

The user can see the number of checks used and the next possible action. A parse error that merely catches malformed syntax does not use a practice check. A successfully parsed wrong answer can consume a check. A worker outage does not use a check or reveal a hint. Repeating the same command key returns the original check and feedback. A new check on the same response may be allowed only by profile. Default is one check per acknowledged response revision set.

## Conditional section routing

A supported branch is a reviewed acyclic graph over section keys. Each branch declares the exact predecessor section, candidate inputs eligible for branching, fixed deterministic rule, ordered thresholds, target keys and a default target. Candidate cannot backtrack across an irrevocable branch boundary unless the policy explicitly defines how to preserve previous branch state and no high-stakes evidence depends on it. Baseline formally graded assessments use fixed sections because otherwise point maxima and equivalent coverage may vary. Formative routing can branch based on concept completion, an explicit choice or a scored threshold.

At a branch boundary, atomically seal the preceding section's acknowledged revisions as a BranchDecisionInput and evaluate with the pinned engine. Compare exact point values or approved rules. If unresolved due to evaluator failure, hold progression and offer support or a published neutral recovery path. Never infer a wrong answer from timeouts. Store eligible inputs, decision outcome, ordered rule ID, target, effective time and route revision. Persist the resolved next section and do not evaluate the condition again on reload. A correction of the branch score later preserves the original route. If the route determines academic evidence, subsequent adjustment requires the official approved case workflow.

Example practice route uses item cluster total 4. Marks below 2 route to remedial section R, 2 through below 4 to regular section S, and 4 to extension section T. Input 2 enters S because the threshold is inclusive. Input unknown because evaluator timeout stays pending. Learner correction after branch does not silently move their route from R to S. A deliberate restart creates a new attempt. The route ID may itself imply a prior outcome, so review whether it can be displayed or interpreted by other learners and staff.

## Installable interactions and scorers

An extension capability manifests renderer family, candidate schema, answer schema, evidence limits, accessibility alternative, scorer contract, compatibility and deprecation date. A delivery capability check verifies actual renderer and evaluator support before start. Unknown or unapproved plugins can be archived and previewed only through safe screenshots or text metadata. Packages cannot inject privileged assessment-page scripts. Approved interactive widgets run in an isolated origin where needed and communicate through a finite typed message protocol with a session nonce, attempt item scope and expected origin. Responses reach the ordinary validation and save layer. The widget cannot finalize an attempt, access keys or grade the learner directly.

A graph plotting plugin can submit bounded points and line descriptors. The exact scoring profile declares coordinate system, tolerance and geometric equivalence. A coding activity queues untrusted code to a separate registered execution boundary with language/build limits, disabled network, read-only fixture mounts, bounded CPU and deterministic test results. Learner code execution is never a generic candidate HTML or evaluator-rule capability. A proof or laboratory demonstration can be manually marked with criterion notes and retained artifact references. Accessibility alternatives must measure the same construct and support independently auditable scores.

Full computer-adaptive testing requires calibrated item models, item exposure controls, uncertainty reporting, stopping rules, access approval and validation of construct equivalence. Treat a CAT implementation as its own later capability. A threshold-based branch is not psychometric CAT and must never be represented as such in reporting or interchange. This distinction prevents unvalidated score comparison across learner routes.

## Candidate confidentiality matrix

| Viewer | Before exam start | During active attempt | After seal, before disclosure | After disclosure |
| --- | --- | --- | --- | --- |
| Candidate | Own availability, timing and permitted rules | Own public form, responses and save states | Receipt and configured state only | Explicitly released fields pinned to a review version |
| Team editor | Own eligibility and approved member list | Shared approved form, saved revisions and participating editor IDs | Shared receipt, subject to current authorization | Authorized shared and individual disclosure projection |
| Supervisor | Candidate access status under roster scope | Clock, progress category and incident actions | Receipt status and authorized incident evidence | No access to marks unless separately granted |
| Blind marker | Assigned queue and opaque label | No candidate answers before seal | Scoped sealed answers and rubric, no roster identities | Same permitted evidence and required correction context |
| Examiner with key permission | Scoped protected keys and authoring fixtures | Scoped protected sources and emergency operations | Same as grant plus explicitly authorized review evidence | Protected historical retrieval under audit |

The visibility matrix applies to exports, analytics, cached mobile views, assistive markup and event feeds. Media signed links do not substitute for entitlement checks. Cache authorized forms privately by Principal, attempt, form and disclosure revision. Invalidate candidate feedback cache when a release pointer changes or a security revocation occurs.
