# 09. Component dependencies, installation, updates and removal

The package assembles cohesive components around native workflows and ownership boundaries. Each persisted record has one owner component. The number of attached views follows that workflow, its schema and the required review surfaces. Dependency declarations specify which parts must be available before a workflow can operate.

## Distinguish the relationships

| Relationship | What it controls | Verification |
| --- | --- | --- |
| Blueprint and source input | JCB definition GUIDs, shared Powers, templates and compiler inputs needed to produce a release | Resolve and pin before compilation. Inspect the generated PHP, manifests and migrations. JCB and its authoring credentials belong to the build environment. |
| Joomla package member | One library, component, plugin or other child carried and installed by a particular package manifest | Verify the exact child type, element identifier, package version, archive name and digest. The child declaration describes packaging and installation order. |
| Mandatory readiness prerequisite | A component consumes a specific provider contract for its required operations | Declare the provider component, exact API major and minimum compatible schema revision. Verify files, schema, migrations, enabled owner service and approved deployment before opening the consumer. |
| Feature prerequisite | An enabled optional operation requires one or more owner components, profiles or outside providers | Resolve the full required closure only for that feature. A missing or unavailable provider blocks the dependent feature while the remaining compatible native operations stay available. |
| Typed GUID relationship | An entity pins or links to a record owned by another component | Verify exact target owner, kind, GUID, institution, version and applicable authorization. The relationship itself says nothing about package install order or service availability. |

Keep the package manifest and the [component map](component-map.json) as separate layers. The map declares architectural ownership and the application's readiness rules. The compiled package XML lists actual child artifacts. The release lock ties those two representations to the exact Joomla, PHP, database, JCB compiler, shared library and child builds that passed deployment tests.

### Component map rules

| Declaration | Required semantics |
| --- | --- |
| `referenced_components` | Catalog-derived, deduplicated set of cross-component entity references. Cycles and references associated with conditional features are expected. |
| `provided_contracts` | A component names each stable runtime interface, API major and schema revision it supports. A registered extension with missing or incompatible tables does not yet provide its declared contract. |
| `required_components` | Explicit mandatory entries naming the provider component, contract, API major, minimum schema revision and reason. Verify the provider declaration and the actually installed compatible build. |
| `activation_sets` | Disjoint sets of mandatory peers that install their own schemas before becoming ready together. Each set names any prerequisite sets. Ungrouped components act as single-member vertices. |
| `feature_dependencies` | Explicit feature key, component prerequisites and required provider profile kinds, where relevant. The implementation also checks the exact enabled integration, package, authoring or exchange profile and its tested behavior. |
| `host_requirements` | Joomla major, approved host and database profiles, shared contracts library and required bootstrap components. The release lock records exact tested version ranges and artifact digests. |

Use the declared component and contract names. Verify exact API major. Treat the minimum schema revision as a lower bound. The release lock and the provider's migration contract must also permit reads and writes at the installed revision. For example, a consumer that supports API major 1 with schema revisions 4 to 6 can use a verified provider at revision 5. It must remain inactive against revision 7 until that combination is explicitly supported. Match package build and migration evidence independently of the displayed extension version.

### True prerequisites and conditional examples

The institution foundation provides host identity binding, scoped authority, durable operations and protected custody. Institution owns the academic role grants and access restrictions. Governance supplies the approved audit, privacy and custody checks. With the required local Joomla issuer in the connector registry, an ExternalIdentity binding needs the institution-owned Principal and that local connection. Creating the connection also needs a verified Institution and accountable authority. Install both schemas, provision the local host connection and approved bootstrap identities behind the common readiness barrier, then enable authentication-dependent LMS operations. The peer dependency is real even though external single sign-on and collaboration integrations can be disabled.

A delivery operation depends on a verified curriculum publication to assign an EnrollmentRelease. Assessment design requires the curriculum owner for its required Course and the item bank for exact item versions. Native marking requires an exact sealed submission and its attempt policy. Shared grade evidence intake can also accept separately authorized manual, package or external evidence. That intake does not require the native attempt component. A grade-release operation checks accepted evidence and the gradebook owner. Ordinary references such as an ActivityVersion pointing at an AssessmentVersion and an AssessmentDelivery pointing at a curriculum placement can form a bidirectional owner graph. The editable course baseline can load without an assessment player. Enabling a native assessment requires its design and delivery contracts. A grade-counting activity additionally needs its approved grade binding, evidence and release path.

| Feature | Readiness when selected | Behavior while unavailable |
| --- | --- | --- |
| Collaboration rooms and class calls | Classroom membership and registered collaboration profile with approved authority and provider tests | Native enrollment, lesson delivery and assessment remain available. Local membership revocation still applies and pending provider removal is visible. |
| Managed documents or media | Protected storage plus an approved adapter that can resolve the exact authorized provider version | Native files continue to work. A required missing external version blocks the affected content or publication pending an approved alternative. |
| Document-assisted model proposals | Native source authoring and an authorized local or external processing profile, scoped egress and private draft review | Direct authoring and previously approved native material continue. A queued proposal retains its draft and review state. |
| Native assessment conversion | Archive import uses transfer, item bank and assessment design. Document-assisted proposal authoring uses its own source workspace and the same native assessment owners | A blocked archive adapter does not block manually authored or document-assisted drafts. An unresolved required assessor prevents publication of that transferred graph. |
| Academic documents and credentials | Grade-derived report cards and transcripts require their grade release and source contracts. Qualification-based and competency-based credentials each require their own approved source and the document issuer | A missing gradebook blocks grade-derived output. An independently authorized credential can still issue from its own approved evidence. |
| SCORM playback and export | Each enabled playback or generation profile verifies the exact edition, implementation build and applicable runner or destination | A player alone cannot satisfy a generator dependency. Keep native learning available and show the unavailable exact package capability. |
| External tools and roster feeds | Registered deployment, credentials, owner scope and tested profile for launch, score return or roster authority. Native roster synchronization needs the delivery owner. It need not install the classroom workspace | A connector failure leaves native work available and cannot erase source grants, enrollments, submissions or grades. |

## Resolve readiness order

1. Read the approved release lock and component map. Check each consumer's declared provider, matching contract major, schema compatibility and package membership. Reject a required self-edge, an unknown component, ambiguous provider declarations or a mismatched build.
2. Collapse members of each declared activation set into one vertex. Reject overlap and missing members. Add edges for mandatory component prerequisites and explicit set prerequisites. Treat consumer to provider as a dependency and process providers before consumers. A cycle across the resulting vertices means the release declaration is blocked. Correct the dependency or explicitly justify a jointly activated set.
3. Build the physical installation list. Put the compatible shared library and foundation bootstrap artifacts before PHP components that load their classes. Within a co-install set use a deterministic file and schema order. A child can create its own tables and register its own interfaces. It cannot boot a peer service or query peer data as if that peer were already ready. Cross-component foreign lookups wait until every participating schema is present.
4. Verify owner services after all schemas in the applicable closure exist. Resolve service interfaces through the owning extension's public provider contract. Use lazy resolution when two ready owners call each other. Constructors, plugin registration and route boot must not recursively activate the whole graph. A dependency error returns a controlled unavailable result instead of a missing-class fatal. [Joomla extension containers](https://manual.joomla.org/docs/next/general-concepts/dependency-injection/extension-child-containers/)
5. Open the readiness barrier only after all mandatory contracts, migrations and authorization checks pass. Then activate optional feature groups independently, with their own documented receipts. Report a feature deliberately disabled, missing an expected dependency, temporarily degraded, or verified ready as different states. An incomplete optional group never sets the whole installation ready for that feature.

Check per-operation owner scope after readiness. For a cross-component GUID, resolve the actual record in the owner service and verify its expected type, institution, exact version, lifecycle and caller's purpose. Require those same checks on lists, autocomplete, modal selectors, API, imports, scheduled jobs, previews, download and direct URLs. Install readiness does not authorize data access. A configured GUID remains an opaque locator. A missing mandatory target blocks a dependent operation. A feature intentionally absent creates no new resources that require its owner. If an existing publication, package registration or issued record already pins an unavailable owner or provider, retain the historical identity, mark the affected operation unavailable and use an approved compatible reader, restore or reviewed alternative. Never reinterpret the missing dependency as no assessment, no evidence or a blank grade.

A command that requires atomic updates across Joomla components uses one authorized orchestration boundary, one database transaction, one lock order and the same owner guards. It does not call arbitrary CRUD endpoints over HTTP. If stores are separate, use the portable staged owner receipts and one visibility barrier. The installed package layout does not turn independent database transactions into one commit.

## Joomla installer and JCB boundary

Joomla package manifests list child extension types and identifiers. The inspected package adapter walks declared children and invokes a separate installer for each. It records package membership through `#__extensions.package_id`. This supplies package delivery and host bookkeeping. The project's mandatory contract and readiness graph is checked by LMS installer and runtime logic. A listed dependency is not installed recursively from an unapproved remote source. Child success and a package database entry do not prove that all schemas, identity seeds or service interfaces are ready. A component manifest selects a script file, initial database SQL and update schema paths where applicable. The inspected adapter runs preflight before copying files and processing SQL on install. On update it applies the extension's declared SQL migration sequence. The installed manifest version and Joomla's schema checkpoint are separate. Require the expected installed tables, columns, indexes, migration state and owner contract version as readiness evidence. JCB component definitions expose matching source and enable fields for install and update preflight and postflight code. Configure both, compile and verify the actual generated hooks and their contract at the exact compiler revision. Preserve maintained installer logic in the blueprint or package source. Test the selected Joomla 6 script interface and generated wrapper. The inspected Joomla adapter accepts a service-provider or InstallerScriptInterface instance, and wraps a legacy class through a compatibility path. Where a pinned compiler emits that legacy path, record it as a verified compatibility dependency of that build. The inspected script adapter treats a false preflight as a failure. Its postflight branch does not abort merely because the hook returns false. Keep the LMS readiness gate closed until checks have passed and have a supported recovery path if postflight reports a failure. The package manifest can request `blockChildUninstall` for its members. The adapter applies that restriction to individual removal outside package removal. It does not decide academic retention, holds or reverse service dependency. Use guarded uninstall preflight as well. The inspected uninstall method ignores an exception from its custom `uninstall` hook and continues cleanup, so that hook cannot serve as the destructive-operation safety gate. ## Installation and readiness

1. **Preflight.** Verify authorized package operation, host and DB profile, signed or otherwise verified release provenance, known dependency closure and clean migration state. Confirm that the exact child archives to be installed are present and match the release lock. Keep the preflight bootstrap able to read the host version, extension records and local release data using Joomla core services alone. It must report a missing LMS library before loading a class that depends on it. For a same-package required child not yet installed, validate the planned incoming artifact and activation set. For a standalone child install, require the compatible installed prerequisites or refuse the unsupported route. Record a protected operator diagnostic.
2. **Lock and fence.** Use a release-scoped deployment lock and maintenance state to prevent concurrent install, update, remove or schema repair. During first installation write-capable routes stay closed. During update keep the previous fully compatible release serving only when its approved read and write compatibility permits. Otherwise stop affected writes before any incompatible migration. Fence old workers and provider dispatch.
3. **Apply local schemas.** Install the package children in the verified order, with each owner applying its own SQL and checkpoints. Do not use component boot as an implicit migration. Record the physical Joomla table prefix, applied schema revisions, migration checksums and completed stages. A Joomla extension entry can exist while readiness is closed.
4. **Seed and reconcile.** After required schemas exist, provision protected foundation configuration, provider contracts, approved ACL actions and unassigned role templates. Create the first Institution only through the platform's `CreateInstitution` command under authorized DeploymentControlPlane bootstrap. Record its approved custody evidence. Do not fabricate a human Principal, bypass host authentication or assign academic authority implicitly to the installer. Seed by stable identifiers and compare existing records instead of overwriting them. Apply relationship backfills and constraints only once prerequisites and ambiguity checks pass. Preserve current institutional configuration, scoped role assignments and retained academic evidence.
5. **Verify and activate.** Resolve owner services, exact schema, required indexes, a scoped actor binding, a rejected cross-institution lookup and a durable receipt transaction. Validate provider features only when enabled. Activate the verified release closure with a versioned readiness marker. Open site writes and scheduled jobs only for scopes backed by current readiness. Bind long-running workers to the active deployment generation and check it again before applying a durable side effect. A process from the earlier generation can finish private computation but cannot commit against the new writer gate.
6. **Report and repair.** If a child, migration, package script or readiness check fails, keep the affected group unavailable. Show what is installed, missing, staged or committed, plus the safe next action and release identifier. Reconcile installed files and schema before retrying the same logical deployment. A restart cannot rerun a verified migration effect simply because the previous response was lost.

Each academic entry point checks readiness before admitting an operation. Default to an authorized maintenance or unavailable response for an incompatible required dependency. A generic readiness page excludes secret references, raw installer file paths from private content, learner information and unredacted provider diagnostics. Staff may inspect scoped deployment evidence without receiving academic record custody.

## Host identity and ACL

Use Joomla for authenticating people, account state, sessions and configured host permissions. The LMS uses one issuer-scoped mapping from the verified host account ID to ExternalIdentity and Principal in the selected Institution. The Joomla user ID is a host subject only. It is never an LMS application GUID or a cross-installation learner key. A Person can exist before any account is linked. Institutional records, enrollment, attendance, assessments, grade release and retention attach to the canonical Person or exact educational record. They do not create an independent LMS password store.

The trusted Joomla adapter obtains the current host identity from the verified session or approved web service authentication. Require a valid local issuer binding, active Principal and permitted Person or service mandate. Use a stable configured issuer identifier for the host deployment. Avoid deriving account identity from a request hostname or email address. If a host account is blocked, deleted or loses a necessary Joomla permission, invalidate affected access and queued delegated authority. Re-check the current host account and LMS scope on protected operations. User lifecycle events can initiate invalidation and reconciliation, with current checks retaining authority even when a notification was missed. Host-account deletion does not cascade to educational records. [Joomla user and authentication events](https://manual.joomla.org/docs/next/building-extensions/plugins/plugin-events/user-auth/)

Use `access.xml` and host ACL as the first operation boundary. `core.manage` controls entry to the administrative interface. Domain commands then evaluate current Institution, Person or service Principal, declared resource scope, active assignment, ownership, lifecycle and separate review or release permissions. The domain does not grant academic custody from Joomla site administration or menu visibility alone. Do not create one host group for every enrollment or grant broad educational access to the default Registered group. Separate host administration, institutional role assignment, guarded operations, student records, grading release and data purge. [Joomla permission actions](https://manual.joomla.org/docs/next/general-concepts/acl/acl-permissions/)

Apply the same command authorization through the administrator screen, site controller, modal selection, API and background jobs. Workers use registered service Principals with exact mandates. A queued job created under a teacher's scope cannot use that teacher's previous privileges after revocation unless an approved durable system mandate applies to the accepted academic operation. Bind every lookup, cache key, projection, export and receipt to the institution and actual visibility policy. An optional adapter has no power to provision a native role grant from its remote user groups.

## Update, compatibility and recovery

| Condition | Required behavior |
| --- | --- |
| Required provider missing, disabled, obsolete or too new | Block consumer activation or update. List exact component, required contract and observed version. Offer a verified compatible package or repair route. Keep the supported prior release active only if it remains coherent. |
| Provider upgrade changes a supported contract | Expand schema, deploy compatible reads and writers, backfill and verify. Switch active version only at the readiness barrier. Retire old fields and paths in a later reviewed contraction. |
| Child installation or migration fails partway | Keep academic write gate closed for the affected closure. Persist completed checkpoints and reconcile actual files, indexes and migration effects before retrying. |
| Learners have active examinations or unreconciled provider effects | Drain, postpone or use an explicitly tested compatible transition. Preserve server deadlines, pinned assessment evidence and one accepted submission. Fence stale workers and reconcile unknown provider effects. |
| Site changed Joomla major, PHP or database configuration | Re-evaluate release compatibility before enabling any incompatible code or writes. Require a reviewed host upgrade and repeat activation checks. |

A package can update several children, and the host can retain partial file or database effects after an interruption. Record an application-level readiness and recovery receipt. Keep a verified database, exact assets and configuration recovery point. Test rollback only where the earlier package reads and writes the migrated data safely. For incompatible or destructive operations use an approved forward repair or coordinated restore. Do not decrement a schema version marker to simulate a rollback. Verify that a restored snapshot reapplies revocations and retained disposition evidence before reopening access.

When reorganizing component ownership during an upgrade, preserve authoritative table and GUID identity where possible. If a table really must move, migrate by a controlled exact owner transfer, maintain both readable forms during validation as required, and switch write ownership once. Verify incoming references, scoped lists, modal routes, API, menus, ACL asset scopes, receipts and revision histories. Installing a new owner with a second writable copy of the data is an invalid migration.

## Removal and retention

1. Require authorized removal planning. Resolve reverse mandatory dependencies and enabled features using the current readiness graph. A referenced component alone does not prove that removing it is safe or prohibited. Also inspect live dependency usage, current learners, retained records and provider effects.
2. For an optional adapter, disable the dependent feature first, stop and fence provider jobs, revoke credentials, and reconcile remote removals. If it is a child of the protected package, the host's blanket child removal guard still applies. Disable it or remove it through a coordinated package change. A separately distributed adapter can use its own guarded removal lifecycle. Preserve course access, local enrollment and academic evidence. A removed optional connector can leave explicit unavailable references for affected resources until reviewed repair.
3. Refuse standalone removal of a required member while a dependent component remains active. Use the package child-removal protection and explicit preflight. For coordinated package removal, close readiness and prepare dependent services before invoking Joomla removal. The package adapter removes manifest children as members of the package. Do not rely on it to sort reverse academic service dependencies. The package preflight checks the removal plan before child scripts can start. Keep child preflight checks able to validate the durable removal authorization even after some services are removed. [Pinned package child removal](https://github.com/joomla/joomla-cms/blob/57655c4c9b1a6008c26e3e919941d63197b11f40/libraries/src/Installer/Adapter/PackageAdapter.php#L381-L413)
4. Preserve retained academic tables, exact asset versions, custody keys, audit and install lineage according to approved policy. Configure and inspect generated uninstall SQL to verify that the ordinary uninstall path has no destructive academic table drop or broad data cleanup. Host-owned menu and extension entries can be cleaned separately. Retain enough evidence to reinstall or restore the supported custody path.
5. Handle destruction through a separate explicitly authorized disposition operation. Check holds, applicable retention, active references, separate approval and external processor effects. Record the applied outcome and evidence. An extension uninstalled or disabled is never equivalent to a verified data purge.

## Deployment acceptance

| Fixture | Passing evidence |
| --- | --- |
| Install the complete institutional package | Exact compatible contracts, schemas and role seeds verified. The foundation activates after its members are ready and no automatic student privileges are granted. |
| Install only a consumer without its mandatory provider | Safe prerequisite error before opening its writes. No implicit provider download or generic route bypass. |
| Interrupt after a foundation child finishes schema setup | None of the activation set opens protected writes. Resume verifies previous checkpoint and completes one readiness outcome. |
| Declare a cycle across independent mandatory sets | Validator rejects release before packaging. A course-to-assessment GUID cycle remains representable. |
| Connect a supported provider with an incompatible API major or missing schema change | Required dependency remains blocked. The readiness diagnostic identifies exact requirement and observed version. |
| Remove collaboration provider while an exam is open | Collaboration is unavailable and pending membership cleanup is tracked. Native attempts and marking continue under their own verified dependencies. |
| Change host identity or role during a queued protected export | Revoked or stale authority cannot generate protected bytes or issue a new download. The prior receipt remains restricted. |
| Upgrade with active attempted work and issued records | Applicable writes are correctly fenced or served by a tested compatible prior version. Accepted work, GUID links and issued records remain traceable and immutable. |
| Attempt direct child uninstall with an active required dependent | Host and custom preflight reject the action. An approved coordinated removal retains academic records and keys under policy. |
| Reinstall after preserved-data removal | Review restores exact owner contracts, host bindings and retained records. No duplicate institution, user binding, course, attempt or grade is created. |

Record test build, component contract versions, observed schema revisions, readiness state, expected outcome and operator evidence. A blueprint design, compiled artifact, Joomla install and verified institutional activation are separate milestones.
