# 06. Export projections and round trips

Editable curriculum, source-compatible exchange, and learner delivery packages have different fidelity requirements. The native relational graph and its immutable revisions remain the source of truth. The primary delivery export action defaults to SCORM 2004 fourth edition when its verified generator profile is installed and the selected material passes its checks. Its profile and edition remain visible and explicit. The author also has a separate native curriculum archive action for backup, relocation and editable re-import.

## Format and edition choices

| Selection | Default use | Required fidelity | Limit |
| --- | --- | --- | --- |
| Native curriculum archive | Editable backup and migration between installations | Typed graph, exact internal references, ordering, asset bytes, pinned definition revisions and permitted assessment settings | Answer-protected definitions, local integrations, private drafts or licensed media require separate export permission. This archive does not include student records. |
| Source-compatible course or library | Reviewed exchange with a destination that implements the chosen source format profile | Documented subset for a verified recipient parser, preserving allowed keys, order and assets | Deferred until a generator and reference re-import test exist for the specific format and edition. A native object with no equivalent mapping remains a blocked or accepted optional difference. |
| SCORM 1.2 | Explicit override for a verified destination that needs the older runtime | Edition-correct manifest, local resources, verified SCO API discovery, declared result/completion policy and resume where supported | No general translation of native availability, assessment or 2004 sequencing. One lesson status does not preserve independent completion and success. |
| SCORM 2004 fourth edition | Default delivery profile, subject to supported feature and destination validation | Matching content aggregation, runtime and declared sequencing coverage. Verify completion and success separately | Native admissions, group visibility, time and academic approvals remain outside the package. Preserve edition limitations in the capability report. |
| SCORM 2004 second or third edition | Explicit destination requirement | Edition-specific verified generator and test fixtures | Disabled until independently tested. Do not relabel a fourth-edition package. |
| Existing package bytes | Approved redistribution, where original authoring bytes and rights are available | Exact original byte digest or separately identified and reviewed normalized derivative | Requires redistribution rights and matching requested edition. Does not yield an editable native course. |

The interface preselects SCORM 2004 fourth edition for portable delivery. If destination testing requires SCORM 1.2, the operator explicitly selects the 1.2 profile and reviews its distinct capability and loss report. If the default profile is unavailable or cannot represent a required feature, show the blocker and require a new supported choice. Do not silently switch editions. The UI does not switch to another edition, add a server dependency, or downgrade a graded activity without a new reviewed plan. Unsupported and unverified formats can be reported by intake without becoming enabled output formats.

## Selection and permission gates

1. Resolve each selected published CourseVersion, library snapshot or independently supported root within one authorized Institution. Pin exact placement, definition, assessment, policy, asset, accessibility and relevant library versions. Reject mutable latest links. Private draft export is a separate permission and defaults off.
2. Traverse the typed graph to build the export selection and dependency set. Select the destination profile, edition, generator build, review policy and options. Hash a canonical ordered selection and projection intent. Source records remain untouched if generation fails.
3. Recheck data classification and rights at prepare, generation and download. A standard student-facing package is independently runnable and inspectable. A scorer, client-side answer key, expected response, hidden branch or embedded variant bank in its files is a disclosure. An export option called `include_answers=false` cannot make a bundled scorer secret. Block the export or choose an explicit approved delivery alternative.
4. Exclude learner identities, enrollments, submissions, grades, records, sessions, imported provider secrets, unreleased grading feedback and private reviews from all curriculum delivery packages. A synthetic launch test verifies that files contain no live records or authorized media URLs. Historic learner transfer uses a separate restricted profile.
5. Validate rights at asset or authored object level. Approved hosting rights need not include redistribution. Material with unknown rights or required protected media blocks delivery packaging until replaced or independently approved. Optional exclusions require a visible report and confirmation.
6. A package requiring a live external service is a separately identified hosted projection, with supported destination launch conditions, transport, privacy, licensing and availability reviewed. Default portable generation denies undeclared network dependencies. Do not silently use a public URL or bundled credentials to preserve behavior.

### Assessment and feature projection

| Source feature | Allowed delivery treatment | When to block |
| --- | --- | --- |
| Text, layout, images and static media | Render accessible structured content with approved local assets and explicit attribution | Required bytes missing, redistribution prohibited, or only available via unapproved origin |
| Keyboard-accessible choice or exact answer, approved low-stakes exercise | Project supported interaction and optional client scorer after approved solution disclosure, and verify behavioral vectors | The course requires confidential solutions, unsupported grading, marking parity without disclosure, or an unverified interaction |
| Numerical or expression scoring | Reproduce only an explicitly implemented portable comparator, tolerance, precision, units and feedback with verified golden vectors | Server-only scoring, stochastic evaluator without equivalent pinned behavior, unsupported expression grammar or inaccessible input |
| Library pool or randomization | Include approved portable finite pool only with exact source revision, permitted disclosure and a tested draw contract. Otherwise require an explicitly chosen frozen form for a compatible delivery purpose | Pool or seed behavior affects high-stakes fairness, answers are protected, or variant contract cannot be represented |
| Essay, file upload, peer review, manual rubric or accommodations | Keep in native workflow, use a separately authorized hosted activity where supported, or publish a clearly labeled ungraded resource if that satisfies the approved objective | Required scored or reviewed work has no parity, and absence would change grades, completion or accommodations |
| Author scripts or an unknown extension | Preserve inertly as authorized restricted source evidence. A source-compatible export can retain such bytes only as an approved inert attachment under the destination profile. Rebuild its behavior before portable export | Never execute or copy an unreviewed source script into generated delivery code |
| Versioned embedded SCORM package | Prefer separate exact approved package redistribution or reviewed independent launch. Native course packaging can reference it without flattening its model | A nested launch, runtime or cross-package grade association has not been tested under the chosen profile |
| Course progress, date and enrollment gates | Project only explicit standard-supported delivery rules. Include limitations and preserve native originals | Required group, grade, calendar or progression behavior would be weakened silently |

A synthetic expression item with points 4 and 1-percent numeric tolerance may be eligible if its comparator is truly numerical and the published portable evaluator matches its inclusive bounds, units and feedback. An item that calls a protected symbolic service cannot be turned into a numeric item on the strength of two examples. If it is required for a graded course, block the portable package unless a verified exact alternative is accepted.

## Export capability and loss manifests

The transfer records an immutable selection manifest, a capability/loss report and a final artifact receipt. The [protected export schema](../interoperability/export-projection.schema.json) defines the selection, capability, loss and validation documents. The [transfer catalog](../interoperability/catalog.json) defines the owning commands and receipt fields. A standard package keeps its required root manifest and validated file structure. Deliver the loss report separately by default. Include a standards extension only when the exact receiving profile permits it and the report has no protected data.

| Artifact or record | Required metadata |
| --- | --- |
| Selection manifest | Institution, destination scope, target format and exact edition, profile revision, generator build, selected root and dependency versions, disclosure options, policy and rights snapshots, selection digest |
| Capability decision | Stable capability ID and version, exact destination mode, required or optional, projection status, owner validation, and required fallback or remedy where applicable |
| Loss entry | Stable issue code, projected source kind and scoped opaque locator, affected root, affected capability, severity, disposition, safe reason and reviewer decision. Restrict source identifiers or assessment evidence to authorized review. |
| Artifact receipt | Export job, output format and edition, exact bytes digest and length, validation reports, generator and profile revisions, build time, result state, private output storage reference and download expiry |
| Round-trip report | Source and destination profiles, canonical projection digests, comparator version, selected semantic comparison rules, counts by mismatch class, reference-player evidence, verified independence from native backend if claimed |

Use distinct decision statuses such as `preserved`, `equivalent_projection`, `delivery_only`, `approved_optional_difference`, `redacted_by_policy` and `blocked`. The report explains why any optional difference is safe for the intended use. A required lost capability blocks generation or delivery. A warning accepted for a native backup does not imply approval for a scored SCORM projection.

Pin approvals to a digest over the selection, report, generator profile and destination. A changed destination, optional exclusion, detector, generator, asset, approved scoring rule or disclosure setting invalidates the approval and requires reevaluation. Do not regenerate the result from a moving latest pointer. A repeated queue or delivery request for the same scope and approved digest reuses the logical job. When deterministic ZIP mode is enabled, stable normalized archive paths, ordering, compression options and entry metadata allow byte comparison. Ordinary compression or archive metadata may differ even when the verified graph does not.

## SCORM package generation and validation

1. Build a portable projection from approved roots, one explicit organization and the chosen launch model. Allocate distinct deterministic manifest identifiers for organization, item occurrence, resource and file. Preserve repeated placement occurrences even when their rendered bytes are equal. Use a single deliverable SCO or multiple SCOs only if the exact edition, runtime and receiving player pass the selected profile. Do not include unrelated source XML or authoring databases.
2. Write `imsmanifest.xml` at the ZIP root with exact edition namespace and metadata. Keep local entry paths, resources, file declarations and dependencies resolvable under a bounded, case-sensitive package index. Treat a plain resource as an asset. It does not issue SCO runtime calls. SCOs bundle the exact approved renderer and runtime bridge for the target edition.
3. Implement the edition-specific initialization, score, status, location, suspend data, commit and termination behavior. Provide an accessible failure and retry path. Use portable opaque bookmarks within edition limits and keep them distinct from native enrollment, gradebook and placement IDs. Avoid claiming that an unload request, queued browser write or tool-side display confirms remote commit.
4. For SCORM 1.2, choose a declared outcome policy. A completion-only SCO sets the approved lesson status such as `completed` and omits optional score data. An approved graded SCO may report a 0–100 normalized score and `passed` or `failed` when finalized. An active or interrupted SCO retains its distinct incomplete state. Document that the single status cannot encode both success and completion independently. Preserve native decision logic outside the package.
5. For SCORM 2004, preserve the approved score projection separately from `cmi.completion_status` and `cmi.success_status`. Map raw, minimum, maximum and scaled values only when valid under the profile. Write sequencing and objectives only for the implemented edition and tested subset. Verify completion or success rollup where claimed. Block native grade weighting, attempts or prerequisite rules that cannot be made equivalent under the destination profile.
6. Independently validate the final archive and selected runtime behavior. Check schemas and local paths, API discovery and state handling, accessible launch, score and completion, suspend/resume, termination and interruption. For 2004 check supported navigation and rollup with reference fixtures. Test an intended destination player where the receiving profile depends on its behavior. Do not describe a package as certified based on schema validation or internal fixtures.

Example. An approved portable exercise awards 14 of 20 with pass threshold 60%. Its SCORM 1.2 profile can write raw score `70` and finalized lesson status `passed`. Its 2004 profile can write raw `14`, min `0`, max `20`, scaled `0.7`, completion `completed` and success `passed`. These are delivery signals. Neither package carries the native learner roster, item weighting history or official grade approval. A destination may still use its own grade interpretation. Record that policy in compatibility testing.

See [SCORM content aggregation](../interoperability/04-scorm-content-aggregation.md), [1.2 runtime](../interoperability/05-scorm-12-runtime.md), [2004 runtime](../interoperability/06-scorm-2004-runtime.md), [sequencing](../interoperability/07-scorm-sequencing.md) and the [ADL fourth-edition test suite](https://github.com/adlnet/SCORM-2004-4ed-Test-Suite) for edition-specific constraints and evidence.

## Round-trip guarantees and limits

| Route | Compare | Safe outcome on difference |
| --- | --- | --- |
| Native curriculum archive exported and re-imported | Canonical typed graph, order, version pins, required links, solution disclosure policy, asset bytes, verified scoring vectors and safe published projection | Identity translation is expected in another tenant. Required semantic mismatch blocks parity. Record optional changes and unknown extensions separately. |
| Source-compatible archive exported and loaded into a verified reference importer | Supported profile structure, source keys and case, ordering, asset locations, published and draft separation, known rubric and assessment semantics | Report different identities and unsupported native metadata explicitly. An untested importer or loss of a required feature prevents compatibility claims. |
| Existing SCORM package redistributed and re-imported | Exact original bytes and verified rights, or approved normalized archive and exact manifest and file digests | Preserve original and derivative separately. A repackaged derivative is a new version. |
| Native curriculum projected to SCORM and imported into a player | Visible content, exact launch structure, approved interactions, permitted score and status behavior, runtime and resume, tested sequencing | Valid playback establishes the declared delivery subset. Re-import creates PackageVersion and an assignable activity. It cannot recover the original editable graph or official academic history. |

A native archive restore remains a curriculum restore even when IDs are mapped and previous snapshots can be re-associated. Preserve lineage so that retries and subsequent source revisions resolve correctly. A projection equivalence test must compare every required edge and setting, using safe normalized representations. It must not rely solely on archive bytes, filenames, counts or screenshot similarity.

A proof set contains invented source fixtures, clean and adversarial assets, placement and library mappings, mathematical boundaries, a recoverable export worker interruption and an intended destination round trip. An approved private curriculum can verify deployment fidelity in restricted custody. Private source materials, derived inventories, snippets, identifiers, hashes, rights evidence and captured screens remain outside public fixtures and CI artifacts.
