# MySQL and MariaDB physical persistence contract

The [relational storage design](01-relational-content-storage.md) applies across platforms. This profile defines a common MySQL and MariaDB representation for a native Joomla implementation. The authored catalogs remain the logical contract. Implementers map their type, nullability, version, key and scope semantics through a compiled schema on each advertised engine.

Use InnoDB with a transactional connection, `utf8mb4` for human text and the approved engine profile. Begin compatibility testing on supported patches of MySQL 8.4 and MariaDB 11.4. Record the exact server, SQL mode, row format, collation, transaction isolation, packet limit and database prefix used for each verification run. Add another version or host configuration after it passes the same acceptance suite. This is the proposed test matrix and carries no runtime verification claim.

## 1. Mapping records and fields

| Portable value | Common physical representation | Read and write contract |
| --- | --- | --- |
| Canonical entity ID | `guid VARCHAR(36) CHARACTER SET ascii COLLATE ascii_bin NOT NULL` with explicit unique constraint | Canonical lower-case hyphenated UUID text, non-nil and exact length. Identity remains immutable across host installs and source transfers |
| Host Table row identity | JCB-generated numeric `id` primary key | Retain local integer behavior and asset integration. Domain APIs and cross-table portable links use application GUIDs |
| Scalar owner or version link | Same `VARCHAR(36)`, character set and collation as target `guid` | Resolve declared target type and same institution. Optional link uses SQL NULL. Prohibit nil, zero sentinel and a mutable current-version alias where an exact revision is required |
| Stable short keys, slugs and locale tags | Bounded ASCII or UTF-8 string with declared canonical format and comparison | Use owner-derived canonical key and matching binary/exact collation where exact identity is required. Keep presentation case separately when the domain has both display and normalized keys |
| Human language and editor labels | `VARCHAR(n)` or `TEXT` under `utf8mb4` with approved text collation | Validate Unicode and logical character limit before writing. Use a separate normalized key or explicitly ordered scope for case-insensitive identity or locale-dependent search |
| Lifecycle and type discriminators | Bounded ASCII string or bounded integer code where the portable catalog defines one | Reject unknown values. Lifecycle changes occur through owner commands. A generated publish toggle cannot release a grade, attempt or native course |
| Boolean | `TINYINT UNSIGNED` with permitted values 0 and 1 | Decode to true or false explicitly. Treat NULL separately where the catalog permits it |
| Revision, counter, sequence and byte length | Unsigned integer sized for the declared maximum, up to `BIGINT UNSIGNED` where needed | Preserve allowed bounds. Compare version counters atomically. Keep server and JSON integer precision contracts consistent |
| Bounded exact decimal | `DECIMAL(p,s)` chosen for the field. For an 18-digit, six-place contract use `DECIMAL(18,6)` | Validate canonical range and scale before binding. Bind and read as decimal text. Apply owner rounding explicitly before storage. Never cast scores to PHP or JavaScript floating point in an exact path |
| Large exact integer or rational | Bounded canonical text or validated typed rational object | Use the owner arithmetic implementation and explicit limits. A rational numerator or denominator that exceeds SQL fixed-point precision stays exact |
| Effective instant | `DATETIME(6)` for UTC instants, `DATE` for date-only values | Convert at the owner boundary. Store zone, civil time and decision policy separately when needed. Reject invalid dates, preserve declared fractional precision and serialize consistently to the API |
| Digest or exact binary key | `BINARY(32)` for an SHA-256 key or equivalent fixed-length representation under the field map | Validate a 64-character lower-case hex input where the API declares it. Bind decoded bytes and return canonical hex text. Compare exact values, including keys for distinct protected objects |
| Canonical structured value | Bounded `LONGTEXT CHARACTER SET utf8mb4 COLLATE utf8mb4_bin` with an explicit enforced `JSON_VALID` check | Parse and validate the exact registered schema, required keys, byte and depth limits in the application. Persist canonical JSON bytes with a separate digest field where the logical record defines one |
| Raw source, documents and large media | `StorageObject` plus scanned bytes in its protected storage backend | Relational rows pin exact immutable storage version, verified media type, digest and scope. Stream bytes without loading them into a SQL model or generic editor |

Each relationship column uses the same type and collation as its target GUID. The application canonicalizes and validates GUID text before either SQL write or query, and the physical profile verifies length and permitted syntax when adding a check. Case or trailing-space behavior of a database collation never decides whether an invalid input is a valid identity. Use distinct typed keys for institution, exact content revision, source object and external provider subject. [MySQL character columns](https://dev.mysql.com/doc/refman/8.4/en/char.html) · [MySQL foreign-key requirements](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)

A logical field can share a name with JCB metadata. Use the [component map's physical mapping](../joomla/component-map.json). The portable identity maps to `guid`. Names reserved by the compiler map to `lms_` plus the logical name. For example, a curriculum `created_by` stores a Principal GUID in `lms_created_by`, `AssetVersion.asset_id` maps to `lms_asset_id`, and `CourseVersion.version` maps to `lms_version`. Local Joomla ACL assets and author IDs continue to use their separate host fields. Apply the same mapping to SQL, selectors, index definitions and API projections. [JCB identity and physical-column checks](../joomla/06-component-allocation.md)

### Optional and nullable values

An absent input field can mean preserve its existing value in a PATCH-style operation. An explicit null is a command input only when its schema and lifecycle allow clearing it. A SQL NULL represents the record's declared unset value. If absent and null have different persisted meanings within a compound object, retain that distinction within the validated JSON value. Never encode a missing GUID as an empty string, zero or a sentinel UUID. Keep receipt replay, draft clear and evidence absence behavior governed by the owner command.

## 2. Canonical JSON and native relational reads

MySQL has a native JSON representation. MariaDB's JSON alias is a text type. Engine JSON behavior and collation choices can change retrieval or comparison details. The common profile uses canonical JSON in text columns for typed compound values and explicit indexed scalar columns for business predicates. This preserves byte-for-byte digest verification and engine-independent equality for sealed content. Use application canonicalization rather than SQL functions to prepare digests. An engine-native JSON optimization requires a separate tested profile and cannot change the public digest or persistence semantics. [MySQL JSON data type](https://dev.mysql.com/doc/refman/8.4/en/json.html) · [MariaDB JSON data type](https://mariadb.com/docs/server/reference/data-types/string-data-types/json)

The writer checks byte size before decoding, rejects duplicate member names before loss of information, validates UTF-8, and bounds depth, array counts, strings and numbers. A generic JSON parser's successful return proves syntax only. The owner then validates the type-specific schema and cross-field invariants. For canonical byte serialization use the relevant declared profile such as RFC 8785. Ordinary PHP object insertion order and an engine's JSON string conversion are insufficient to claim canonical serialization. Keep exact decimal strings, digest fields and semantic array order consistent with the declared profile.

Use a narrower per-field request and storage limit than the database type permits. Budget for the decoded form, copies during validation, indexes, query result and typical concurrent exam workload. A content payload that contains many locale variants still obeys a declared aggregate byte limit. Check connection and server packet limits against the accepted application request budget. A too-large document fails before partial persistence and includes a safe field-level diagnostic. Large file bytes go through the protected storage interface.

Prefer an indexed authoritative scalar when a value participates in owner checks or SQL joins. A derived field for search or projection can duplicate a property only when its source, rebuild and consistency rules are explicit. For example, a picker title can derive from the default approved locale. A reference usage row can derive from an exact immutable payload and publication. Both maintain clear derivation provenance. Never use a loosely typed JSON search as the only institution filter, retention check or item authorization predicate.

## 3. Constraints and indexes

Declare every logical key and query index from the catalog in the physical schema plan. Name SQL constraints using bounded deterministic tokens. Verify that the installed schema matches the plan through metadata and real failure tests. Use a unique constraint for application GUIDs and for owner-scoped business keys. An ordinary generated index with a descriptive name gives query support and cannot enforce uniqueness.

A same-component foreign key uses the declared target and a unique target key. Parent and child types and collations match exactly. Prefer `RESTRICT` for published versions, approved evidence, source identifiers and issuance records. For cross-component relations, use the typed owner contract and same-transaction checks. These references remain logical by default so package installation, component compatibility and retention are controlled by their owners. Add a physical cross-component foreign key only after verifying schema order, same-engine requirements, migrations and removal semantics. SQL identity existence does not prove enrollment, visibility, institutional scope or active status. [InnoDB foreign-key checks and timing](https://dev.mysql.com/doc/refman/8.4/en/ansi-diff-foreign-keys.html)

MySQL and MariaDB nullable unique-key semantics allow multiple null key members. Preserve the intended business rule using an explicit non-null scope key where the catalog requires equality at the root. The outline records already define `sibling_scope_key`. Derive it as `root` or `parent/` plus the canonical UUID of the parent key appropriate to the record. Do not let clients set this field or rely on NULL to make root placement positions unique. For other nullable keys, apply the exact owner policy. Some fields intentionally allow any number of unset values.

Long source identifiers can exceed the supported engine index width. Keep the exact original tuple in authoritative fields and follow the [wide natural key digest contract](../joomla/06-component-allocation.md#wide-natural-keys-and-exact-comparison) for equality uniqueness. Verify full tuples on read and conflicts. Choose indexed prefixes for bounded performance hints only. Never substitute a truncated key for a uniqueness guarantee. Add a separate orderable index when the workload needs range scans and pagination.

| Query | Leading key or covered lookup | Validation and projection |
| --- | --- | --- |
| Open learner's active release | `EnrollmentRelease(enrollment_id, effective_from, effective_to)` | Scope the enrollment through Person and offering and apply the exact effective instant. Any overlapping effective releases fail closed |
| Locate one lesson occurrence | Unique `ContentPlacement(course_version_id, placement_key)` | CourseVersion comes from the authorized release. Fetch exact node/activity/rule references and required state |
| Fetch ordered children | Unique `ContentPlacement(course_version_id, sibling_scope_key, position)` | Limit to the resolved parent's exact scope. Order by position and resolve each version by typed GUID |
| Load authorized item form | `InteractionDefinition(item_version_id, display_order)` with exact AttemptItem pins | Return the public field projection and approved stimulus only. Resolve scoring bindings through a separate protected query |
| Read most recent saved response | `ResponseRevision(attempt_item_id, interaction_key, revision)` | Latest revision from the authorized attempt. Validate the requested item and interaction before returning candidate-owned evidence |
| Find a released grade | `GradeReleaseEntry(enrollment_id, grade_result_id, visible_from)` | Verify release visibility and exact result revision. Exclude pending calculation and reviewer records |
| Resolve or stage transferred identity | Unique source mapping tuple or its exact digest projection | Verify institution, source scope and kind, full key, applicable revision and the expected target owner |
| Scan expiry or claim task work | The catalog state/deadline or queue kind/state/available-time key | Limit batches and enforce worker scope, fencing and exact state before updates |

Keyset paginate with a stable tie-breaker. Include tenant and capability dimensions in both list and count queries. Validate the actual explain plan with representative row counts and mixtures of published and draft content. Scan and retention exports can use background cursors. An authoritative interactive read must not perform unbounded scans of serialized payloads. Fetch bounded parent pages before large body values. Batch exact version lookups per record type and use placeholders for all values.

## 4. Transaction patterns

Use one database transaction for an owner command that changes a version, writes evidence and produces a receipt or outbox event. Keep a single connection across the involved owner tables. An authorization check that depends on a changing row rechecks after obtaining the necessary locks or compare-and-swap. Validate request schemas and compile read-only candidates before beginning expensive transactions. Revalidate their digest and current scope under the lock. Avoid file retrieval, provider calls, long math computation and archive compression within a lock window.

Read committed with explicit row locks is the common command profile. Verify the selected isolation on the actual Joomla connection. Immutable publication pins can be gathered in bounded batches when the contract declares the exact read vector. A consistent report or transfer that requires a live cutoff uses a stated snapshot or a reproducible sealed source vector. A copied read replica is suitable only for projections with their declared staleness behavior. Do not check an exam deadline, current enrollment or authoritative receipt against a lagging replica.

A replay key includes institution, principal, operation, target scope and request key. Verify the actor's current authorization before disclosing a stored replay result. Equal key and canonical payload digest replays the stored result. Reusing the key with changed content returns a conflict. Reserve the receipt and lock the domain aggregate in the documented operation order. Insert receipt, domain effects and outbox together. On rollback there is no success receipt. A client that times out after a commit retries the same key and bytes. Cross-domain consumers use durable inbox deduplication and source sequence checks.

Publish lock order for each workflow. Where an edit changes an asset reference that affects removal, define a shared dependency lock order and have both writers and retire/purge operations take the same target lock. Lock multiple keys in a consistent sorted order after resolving the candidate set. Use the stable application ID plus type to sort identity sets. On deadlock or lock timeout roll back the entire transaction, then retry the same command with bounded jitter where its idempotency contract permits it. Never reuse a partially applied in-memory mutation after a database failure. [MySQL locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) · [MySQL deadlock guidance](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html) · [MariaDB FOR UPDATE](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update)

### Concurrent reordering without changing IDs

A draft reorder compares its exact revision and then locks CourseDraft and the affected sibling sets. Compute and validate the complete desired positions and links, including removals, before touching the stored rows. The logical editor accepts positions 0 through 511 under the catalog's rule. To swap positions safely under immediate unique enforcement, reserve physical positions 512 through 1023 for this transactional reorder only. The owner shifts existing rows in the affected sibling scopes into that disjoint band, applies the validated final assignments and removes only approved editable rows. Persisted occurrence GUIDs remain unchanged. Moving a row updates its parent and derived sibling scope with the final order.

The physical column and check permit both bands. The owner verifies no staged positions remain before advancing the draft revision or writing a receipt. Generated generic writes that could set a staging position are disabled. On any failure the transaction rolls back to the original tree. A release insert uses only the final 0 through 511 band and never performs a mutable sibling reorder. Test the two-row swap, concurrent child insert, inter-parent move and a failed operation after the staging update.

### Asynchronous jobs and package commits

The job worker claims a small batch using indexed queue state. Use `SKIP LOCKED` only after verifying the exact engine and access pattern, and only where skipping currently locked candidates does not affect academic ordering. A portable fallback selects a bounded candidate list and atomically changes a candidate's current state and fence. A worker verifies its job identity, lease, generation and exact input revision before accepting output. Leave result and event writes in the owner transaction. Scoring and transfer workers execute outside the request lock and use typed evidence under the pinned evaluator or adapter release.

The SCORM runtime locks its authorized registration, launch session and occurrence state in its stated order. It compares exact fence, epoch and mutation sequence. A durable commit atomically records accepted mutations, current state, receipt and outbox. Browser calls and package origin rules are documented separately. Native assessment writes use their Attempt lease and response revision contracts. Both store academic evidence on the server before acknowledging durable success.

## 5. Installation and migration

The [JCB runtime composition chapter](../joomla/07-runtime-composition-and-format-boundaries.md) identifies maintained source for fields, hooks, generated schema and migration logic. Generated artifacts are inspected and recompiled from their source. Keep the schema version and the owner record's academic version separate. SQL schema migrations never rewrite the meaning or identifier of a published course, accepted attempt or issued grade.

1. Preflight the server family/version, `utf8mb4`, required collations, transactional engine, UTC settings, strict data validation, metadata locks, selected packet budget and schema privileges. Capture the actual installed index and collation inventory. Verify the target enforces declared checks with a negative fixture. Reject unsupported layout or disabled constraint enforcement before applying dependent DDL.
2. Install the required component schemas and shared mechanics, with academic writes gated until ready. Produce a manifest of expected columns, keys and versioned migration identifiers. Circular references resolve after all required tables exist. Apply physical constraints only where the owner policy calls for them.
3. For an upgrade, back up and verify the recoverable starting state. Use expand-and-contract changes. Add compatible columns and indexes, write old/new representation where needed, and backfill using scoped keyset batches with resumable checkpoints and exact hashes. Keep credentials, files and protected evidence out of migration logs.
4. Inspect and reconcile conflicts before applying `NOT NULL`, uniqueness or enforcing new lookup paths. Verify any records with unmatched sources, malformed JSON, incorrect collation or key collision. Reject a conversion that would silently pick a different source row.
5. Validate the installed constraints and run a role-scoped sample workflow. Change schema readiness only when required owners, workers, views and APIs accept the target manifest. Confirm skipped-version upgrade and partial-run retry.
6. Remove old columns or indexes in a later migration after all compatible readers and writers have switched and recovery requirements are met. Keep long-running asynchronous workers fenced against old schema semantics.

A DDL statement can commit a transaction independently of application state. Atomic handling of one statement on some engines does not make a multi-step migration atomic. Perform each statement against a verified precondition, capture its checkpoint, and reconcile metadata after interruption before resuming. Avoid enclosing DDL and critical data edits in the same rollback assumption. [MySQL atomic DDL](https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html) · [MariaDB statements that cause implicit commit](https://mariadb.com/docs/server/reference/sql-statements/transactions/sql-statements-that-cause-an-implicit-commit)

Use the authorized transfer or equivalent logical backup process when moving between engines. Test equivalence of canonical structured values, exact decimals, binary digests, required null semantics and immutable evidence on the destination. Never assume physical files, native JSON binary representation, database sequence values or engine-specific generated columns can move unchanged.

## 6. Database acceptance matrix

| Case | Required evidence on each supported engine |
| --- | --- |
| Canonical GUID and scope | Valid exact GUID joins and duplicates fail. Case, spaces and nil fail the public owner boundary. A known foreign GUID from another institution cannot resolve as a valid reference |
| JSON and Unicode | Common canonical bytes and SHA-256 for Unicode text, choice order, nested math and labels. Invalid UTF-8, duplicate members, unknown versions and excessive resource use fail before write |
| Exact numbers and dates | Accurate decimal scale, null/zero distinction, response lexeme preservation, rational grade arithmetic and fractional UTC timestamp round trip |
| Nested editing and version pinning | Concurrent swap, cross-parent reorder and failed partial-save preserve invariant, identities and approved published scope |
| Composite key | Boundary-length external identifiers use verified complete tuple semantics. Both real duplicate and different full tuple with an injected digest collision follow the specified paths |
| Concurrency | Same-key receipt replay yields one result. Two conflicting requests preserve one authoritative revision. Retry after deadlock or uncertain outcome changes no accepted evidence |
| Authorization and indexing | Real row lists use institution and exact owner context. Explain plans exercise selected lookup keys and published/private field projections |
| Migration | Fresh installation, skipped-version upgrade and killed DDL/backfill resume from discovered checkpoints. Sealed identifiers, digests, asset versions and grades survive logical engine migration |
| Durability | Database and object backup restore produces matching artifacts, learner submissions and publication manifests. Revoked and quarantined resources remain protected |
